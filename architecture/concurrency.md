# Goroutines and channels

One premise of the project ([`grober_plan.md`](../grober_plan.md)) was to try
Go's concurrency on a real problem: rules as concurrent observers, parallel
work on puzzles, puzzles prepared before anyone asks for them. This file is a
guided tour of every place that starts goroutines or uses channels, meant for
developers who want to study the patterns. It explains the shape of each one
and why it has that shape. The code and its comments have the details; names
are given as `package.Function` so they can be found with grep.

Principle 1 of [README.md](README.md#2-principles-that-shape-the-code)
(the board is monotone) is what makes most of this safe: a cell only goes from
free to star or cross, so marks can arrive in any order and be duplicated, and
every goroutine can work on its own copy of the board without locks.

Every section shows one run of its pattern as a sequence diagram: a column
per goroutine, channel and other shared state, time downwards, one band per
numbered step. A solid line is a running goroutine, a dashed orange one a
blocked goroutine, labelled with what it waits on; a bar on a channel is a
value in its buffer, a grey bar on a mutex the time it is held. The same run can be stepped through as an animated scene in
[`concurrency/player.html`](concurrency/player.html), opened in a browser.

Both are drawn from a *story* in `internal/concviz`: a script of steps played
on a small model of Go's semantics (buffers and handoffs, `select` with and
without `default`, `close` as a broadcast, `sync.WaitGroup`, `sync.Once`,
`sync.Mutex`), so
who blocks and who wakes up follows from the operations instead of being
drawn by hand. Every operation also names the code it stands for, and a test
checks these names against the source with `go/ast`: renaming a channel,
changing a capacity or dropping a `select` case fails it until the story
follows ([decision 24](decisions/24-concurrency-animations.md)). A run shows
one possible interleaving; the scheduler may choose others, which is why the
code does not depend on any of them.

## 1. Concurrent rule runner (`internal/solver/concurrent.go`)

The showpiece and the original experiment. Every observer (rule) runs in its
own goroutine; a single runner goroutine owns the authoritative board.

```
observer goroutines --(msg: marks / idle / done)--> runner --(delta batches)--> mailboxes
```

<!-- concviz 01-concurrent-runner: generated by go test ./internal/concviz -update -->

![Sequence diagram: 1. Concurrent rule runner: actors, mailboxes, quiescence](concurrency/01-concurrent-runner.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#01-concurrent-runner) in a browser.

1. RunConcurrent starts one goroutine per observer with wg.Go. Each works on its own copy of the board, at version 0.
2. The runner is the only reader of out. It blocks until a message arrives.
3. B finds marks first and sends them; the runner keeps them pending: A has a lower level and is not idle at v0 yet.
4. A finds marks too. The lowest level goes first: the runner applies A's marks, version 1. B's pending marks are stale now and dropped.
5. Broadcast: put appends batch v1 to each mailbox and does a non-blocking send on notify. The runner never blocks here.
6. Both observers wake up and take their whole queue. A is quick; B's rule is slow this time.
7. A sends new marks. No simpler rule exists, so the runner applies them at once: version 2.
8. Broadcast v2. A wakes up. B is busy, so its wake-up waits in the 1-slot buffer of notify.
9. A catches up and finds more marks: version 3.
10. Broadcast v3. B's notify slot is still full, so this wake-up is dropped; batch v3 is queued all the same.
11. Meanwhile B reports marks from v1. The runner is busy, but out has room for one message per observer: B does not block.
12. The runner reads B's message from the buffer. Marks found on v1 are stale at v3 and ignored: B will deduce again.
13. B's select finds the pending wake-up without blocking. take returns v2 and v3 together: one wake-up was enough.
14. Neither finds anything new: both report idle at v3 and wait for the next broadcast.
15. Every observer is idle at the current version, so nothing is in flight. The deferred close(quit) wakes both at once; wg.Wait waits for them.
16. The observers return; wg counts down to 0 and wg.Wait returns. No goroutine outlives RunConcurrent.

<!-- /concviz -->

- **Fan-in.** All observers send on one channel `out chan msg`. The runner is
  the only reader and never stops reading while it runs, so observers cannot
  get stuck on a send.
- **Unbounded mailboxes, not channels, for the way back.** The runner must
  broadcast each delta to every observer without ever blocking (if it blocked
  on an observer that is itself blocked sending to the runner, both would
  wait forever). A buffered channel cannot guarantee that for any fixed size,
  so `mailbox` is a mutex-protected slice plus a `notify chan struct{}` with
  capacity 1. `put` appends and tries a non-blocking send on `notify`; if a
  wake-up is already pending, the new one is dropped because `take` returns
  everything queued anyway. This "slice + 1-slot notify channel" is a
  common way to build an unbounded queue in Go.
- **Private state per actor.** Each observer keeps its own clone of the board
  and applies the deltas from its mailbox in order. The board is monotone, so
  after applying all batches up to version *v* the copy equals the runner's
  board at *v*. No locks around the board.
- **Shutdown by `close(quit)`.** Closing a channel wakes every receiver at
  once, so it serves as a broadcast. Both blocking points of an observer (the
  send on `out` and the wait on `notify`) `select` on `quit` too. The runner
  `defer`s `close(quit)` followed by `wg.Wait()`, so no goroutine outlives the
  call, whichever way it returns (solved, stuck, contradiction).
- **Termination without a central clock.** Detecting that "nobody can deduce
  anything any more" is the hard part of any actor system. The runner gives
  each published state a version number; an observer that finds nothing
  reports `Idle` with the version it has seen. Messages from one goroutine on
  one channel arrive in order, so once every active observer is idle at the
  current version, nothing is left in flight: the fixpoint is reached.
- **Priorities on top of parallelism.** Marks found on the current version
  wait in a pending set; the runner applies the one of the lowest level only
  once every simpler observer is idle at that version
  ([decision 6](decisions/06-priority-levels.md)). The goroutines keep
  computing in parallel; only the order of application is serialised. Marks
  computed on an older version are dropped, because their senders will see
  the newer broadcast and deduce again.
- **Rules know nothing of this.** `runObserver` wraps the pure
  `Observer.Deduce`; concurrency lives in the runner only (principle 2).

`starbattle solve` uses this runner by default. The explanations people see
come from the deterministic `RunSync` instead, because the concurrent step
order, and so the length of a chain, varies between runs
([decision 2](decisions/02-sync-runner-for-trial-runs.md)).
[refactorings.md](refactorings.md) explains why the runner stays.

## 2. Parallel lookahead (`solver.lookahead`, `internal/solver/search.go`)

When the rules are stuck, the solver tries a star on every free cell and keeps
the refutation that is easiest to follow.

<!-- concviz 02-lookahead-pool: generated by go test ./internal/concviz -update -->

![Sequence diagram: 2. Parallel lookahead: a worker pool, results by index](concurrency/02-lookahead-pool.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#02-lookahead-pool) in a browser.

1. The rules are stuck; four free cells c0 to c3 are candidates. lookahead makes hyps with one slot each and an unbuffered jobs channel, and starts GOMAXPROCS workers (two here).
2. It sends the indices one by one. Each send is a handoff: index 0 to worker 1, index 1 to worker 2. Each tries a star on its cell, on its own copy of the board.
3. Both workers are busy, so the send of index 2 blocks until one of them comes back to its range loop.
4. The star on c1 leads to a contradiction in 5 steps. Worker 2 writes the chain into hyps[1]: its own slot, so no lock and no channel.
5. Worker 2 takes index 2, which releases the caller. Its send of index 3 blocks again.
6. The star on c0 leads to no contradiction: hyps[0] stays nil. Worker 1 takes index 3, and the caller closes jobs and waits.
7. c2 and c3 both lead to a contradiction in 3 steps. Each worker writes its slot, and its range ends on the closed, empty jobs: it returns.
8. wg.Wait returns: every write to hyps happened before it, so the caller can read them all without a lock.
9. The best chain is picked in index order with a strict comparison: c2 beats c1, and the tie with c3 keeps the earlier c2. Which worker finished first never matters.

<!-- /concviz -->

- A classic **worker pool**: `GOMAXPROCS` workers range over an unbuffered
  `jobs chan int`; the producer sends the indices and closes the channel,
  which ends every worker's `range` loop; `wg.Wait()` waits for the rest.
- **No results channel.** Each worker writes to `hyps[i]`, its own slot of a
  pre-sized slice. Distinct indices need no lock, and `wg.Wait()` establishes
  the happens-before edge for reading them afterwards.
- **Determinism despite scheduling.** The best hypothesis is picked after
  all are done, by a strict comparison in index order, so ties keep the
  earlier candidate. Which worker finished first never matters. Inside a
  trial the deterministic `RunSync` is used, for the same reason.

## 3. Parallel generator attempts (`generator.run`, `internal/generator/generator.go`)

Generating a uniquely solvable puzzle is a series of random attempts, many of
which fail. Running several at once helps, but the result must depend only on
the seed (principle 5). See [decision 13](decisions/13-parallel-generator-attempts.md)
for the measurements.

<!-- concviz 03-generator-attempts: generated by go test ./internal/concviz -update -->

![Sequence diagram: 3. Parallel generator attempts: semaphores, a deterministic winner](concurrency/03-generator-attempts.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#03-generator-attempts) in a browser.

1. run with 2 workers: slots (capacity 2) limits this call, cpuSlots (GOMAXPROCS−1, 3 here) every call in the process together. Another call, the server's pool, holds one already.
2. Attempt 0: acquire is a send into each buffer. Then the loop checks best and Done (a select with default), and starts the attempt with its own random generator.
3. Attempt 1 the same way. Now both buffers are full: three attempts run in the process, two of them from this call.
4. For attempt 2 the send on slots blocks: a buffered channel is a counting semaphore, and its buffer is full.
5. Attempt 1 succeeds first. It writes results[1] and lowers best from 1000 to 1 with a compare-and-swap loop.
6. Its deferred release receives from cpuSlots, then from slots. That frees the loop: its waiting value moves into the buffer of slots.
7. The loop acquires cpuSlots too, but 2 > best: attempt 2 would lose anyway and is not started. It releases both and waits for attempt 0.
8. Attempt 0 goes on: its index is below best, so it can still win. It succeeds, writes results[0] and lowers best to 0.
9. run returns results[0], the lowest successful attempt: the same puzzle as with one worker. More workers only make it arrive sooner.

<!-- /concviz -->

- **Buffered channels as counting semaphores.** `slots := make(chan
  struct{}, workers)` limits this call; the package-level `cpuSlots` (size
  GOMAXPROCS − 1) limits all calls of the process together, so the server's
  background pool and a request never take every core. Acquire is a send,
  release a receive, in reverse order, in a `defer`.
- **Deterministic winner.** Attempt *i* draws its own random generator from
  the seed in order, before it starts. The successful attempt with the lowest
  index wins, tracked in an `atomic.Int64` updated with a compare-and-swap
  loop ("atomic minimum"). Attempts above the current best are not started,
  and running ones give up at their next check (`stop`). So more workers only
  make the result arrive sooner, never different (`TestWorkersSameResult`).
- **Cancellation by a `Done <-chan struct{}`** in `Options`, polled with a
  non-blocking `select` (`cancelled`). The generator takes a bare channel, not
  a `context.Context`: it only needs the "stop" signal, and callers pass
  `ctx.Done()` or `r.Context().Done()`.

The lookahead of section 2 is not covered by `cpuSlots`.

## 4. Hard puzzle search (`hardsearch.Search`, `internal/hardsearch/hardsearch.go`)

`starbattle hardsearch` checks a range of seeds for puzzles that defeat the
rules, on all cores, and must print and write them in seed order so a run can
be continued where it stopped.

<!-- concviz 04-hardsearch-pipeline: generated by go test ./internal/concviz -update -->

![Sequence diagram: 4. Hard puzzle search: ordered pipeline, cancellation](concurrency/04-hardsearch-pipeline.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#04-hardsearch-pipeline) in a browser.

1. Search makes two unbuffered channels and starts two workers with wg.Go. Each ranges over jobs and blocks: nothing is sent yet.
2. It starts a producer and a closer, which waits for the workers. The caller itself ranges over results.
3. Unbuffered means every send is a handoff to a waiting receiver: seed 10 goes to worker 1, seed 11 to worker 2.
4. No worker is free, so the producer blocks in its select until one takes seed 12 or the context is cancelled.
5. Worker 2 finishes first. Seed 11 is out of order: the caller keeps it in the reorder buffer.
6. Worker 2 asks for the next seed: the producer's waiting send completes. It offers seed 13 and blocks again.
7. Worker 1 delivers seed 10. Now 10 and 11 are in sequence: the caller emits both, from one goroutine, and writes their files.
8. Worker 2 finishes seed 12 while the caller is still writing. Its send must wait: back-pressure through the unbuffered channel.
9. Ctrl-C cancels the context: ctx.Done() is closed. The producer's select wakes up and returns; its deferred close(jobs) follows.
10. The caller takes seed 12 and emits it. Worker 2's range over the closed jobs ends: it returns, wg counts down.
11. Seed 13 comes back with an error because it was cancelled. The caller drops it: a gap where the run ends.
12. The last worker is gone, so wg.Wait returns and the closer closes results. That ends the caller's range loop.
13. Search returns 13, the first seed not emitted: -from 13 continues the run without holes.

<!-- /concviz -->

- **A three-stage pipeline.** A producer goroutine sends seeds on `jobs`
  (`select` with `ctx.Done()`, `defer close(jobs)`); `workers` goroutines
  turn seeds into results on `results`; a third goroutine waits for the
  workers and closes `results`. The caller's goroutine ranges over `results`.
  "Close the results channel from a goroutine that waits on the WaitGroup" is
  the standard way to let a consumer use `range` over a fan-in.
- **Reorder buffer.** Results arrive out of order; a map holds them until the
  next seed in sequence is there, so `emit` is called in seed order and from
  one goroutine only (the caller needs no locks).
- **Resumable cancellation.** Ctrl-C cancels the context
  (`signal.NotifyContext`); the producer stops, running seeds abort through
  the generator's `Done` channel, and their errors are discarded. `Search`
  returns the first seed it did not emit: the gap left by an aborted seed
  ends the run, so `-from` with that seed continues without holes.
- **Back-pressure for free.** Both channels are unbuffered, so a slow `emit`
  (writing files) slows the workers instead of piling up results.

## 5. Design completions streamed to the page (`designer.completeDesign`)

The developer tool `starbattle design` completes a drawn pattern *k* times
with different seeds, and the page shows each candidate as soon as it exists.

<!-- concviz 05-designer-stream: generated by go test ./internal/concviz -update -->

![Sequence diagram: 5. Design completions streamed to the page: fan-out, a buffer of k, a waiter](concurrency/05-designer-stream.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#05-designer-stream) in a browser.

1. The page asks for 3 completions. completeDesign makes out with a buffer of exactly k = 3 and starts one goroutine per candidate.
2. It also starts a waiter that will close out after wg.Wait, and returns out at once. The handler ranges over it, still in the same request.
3. Candidate 2 finds a puzzle first. Under the mutex it records the layout in seen; the lock only guards the map.
4. It sends the result: the handler is waiting, so it is a handoff. The page shows the first candidate while the others still run.
5. Candidates 1 and 3 finish together. 1 takes the lock; 3 must wait for it.
6. 1 has a new layout and unlocks: 3 gets the lock and finds its layout already in seen, a duplicate.
7. Both send while the handler is still writing. With room for k values, no send can block, not even if the page is gone.
8. The last candidate is done, so wg.Wait returns and the waiter closes out. Values already in the buffer stay readable.
9. The handler drains the buffer: it counts the duplicate and writes candidate 1. Then range ends on the closed, empty channel.
10. The handler writes the summary line and returns. Closing the page instead would have cancelled r.Context(), which the generator polls.

<!-- /concviz -->

- **Fan-out, stream back.** One goroutine per candidate (each runs the
  generator with `Workers: 1`, the candidates are the parallelism, and all
  share `cpuSlots`). Results go into `out`, which the function returns as a
  receive-only `<-chan *foundCandidate`. The HTTP handler ranges over it and
  writes one NDJSON line per candidate, flushing after each.
- **A buffer of exactly *k*.** Each goroutine sends exactly once, so with
  capacity *k* no send can block, even if the reader is gone. A waiter
  goroutine closes `out` after `wg.Wait()`, which ends the handler's loop.
- **Cancellation from the browser.** The request's `r.Context().Done()` is
  passed to the generator, so closing the page stops the work.
- A small mutex guards the set of seen layouts that marks duplicates; the
  channel carries the results, the mutex protects shared state. Both have
  their place.

## 6. Pre-queueing puzzles (`web.Pool`, `internal/web/pool.go`)

`serve` keeps one generated and solved puzzle per size ready, so "new puzzle"
answers at once.

<!-- concviz 06-pool-queue: generated by go test ./internal/concviz -update -->

![Sequence diagram: 6. Pre-queueing puzzles: a buffered channel as a deduplicating queue](concurrency/06-pool-queue.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#06-pool-queue) in a browser.

1. serve calls NewPool for every size (three here: 5, 6 and 7). It queues them smallest first: the capacity is the number of sizes, so these sends never block.
2. It starts one fill goroutine for all sizes and returns; serve goes on. fill ranges over the queue and takes 5.
3. The 5×5 puzzle is ready. fill stores it under the mutex, then takes size 6. The generator inside is already parallel, so one fill goroutine is enough.
4. A player asks for a new 5×5 puzzle. takePuzzle takes the mutex. Meanwhile fill finishes 6×6 and has to wait for the mutex.
5. The request hands out the ready 5×5 at once and queues 5 for a refill, still holding the mutex. That send cannot block: 5 was not in the queue while its puzzle was ready.
6. It unlocks, which lets fill in to store 6×6. The player already has their puzzle.
7. fill works through the queue one size at a time: 7, then 5 again. Each size is queued at most once, so the queue never needs more room than one slot per size.
8. Every size is ready. The queue is empty and fill blocks in its range until the next puzzle is handed out, for as long as the server runs.

<!-- /concviz -->

- **A buffered channel as a work queue.** `queue chan int` holds the sizes to
  (re)fill; a single background goroutine ranges over it, filling the sizes
  one at a time, smallest first (they are queued in that order at start).
- **Deduplication by invariant.** The capacity is the number of sizes, and a
  size is queued only when its puzzle is handed out, i.e. when it is neither
  ready nor queued. So a size is in the queue at most once, the queue never
  has more entries than its capacity, and `takePuzzle` may send on it while
  holding the mutex without risk of blocking (the comment says so at the
  send).
- One goroutine for all sizes, on purpose: the generator is already parallel
  inside (section 3), and the pool should not compete with requests.

## 7. Preparing the next party puzzles (`party.Manager.startPrep`)

A party prepares the puzzle of its next round (in the clock mode several
ahead) in the background while players play. It is included here as a
deliberate contrast: there is **no channel**. The party's state already lives
behind the manager's mutex ([README.md](README.md#4-where-state-lives)), so
the goroutine takes the lock to read what is needed, releases it around the
slow `prepare`, and takes it again to store the result.

<!-- concviz 07-party-prep: generated by go test ./internal/concviz -update -->

![Sequence diagram: 7. Preparing the next party puzzles: a mutex and a generation number, no channel](concurrency/07-party-prep.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#07-party-prep) in a browser.

1. A player creates a party against the clock, which keeps 3 puzzles ready. Create holds pm.mu; startPrep bumps prepGen to 1 and starts a preparer that keeps its own copy, gen = 1.
2. The preparer needs the lock to read the party. Create still holds it, so Lock blocks until Create returns.
3. prepGen is still 1, so the preparation is current. It picks a size and unlocks: the slow part runs without the lock, and requests are not held up by the generator.
4. The puzzle is ready. With the lock held again it checks prepGen (still 1), appends the puzzle, signals the streams (update), and goes for the next one.
5. Everybody has left. Later Tick, under the lock, finds the party idle: it deletes it, bumps prepGen to 2 and signals the streams a last time.
6. prepare cannot be interrupted, but when it is done and the preparer holds the lock, prepGen 2 ≠ its gen 1: it unlocks and returns, and its puzzle is never used.
7. No channel was needed: the party lives behind pm.mu anyway. When the state is behind a mutex, a generation number is simpler than a cancel channel.

<!-- /concviz -->

Cancellation is a **generation number**: `prepGen` is incremented when a
preparation must be dropped (e.g. the party expired); the goroutine compares
its own copy each time it holds the lock and quietly ends on a mismatch. It
cannot interrupt a running `prepare`, but its result is never used. When the
state is behind a mutex anyway, this is simpler than a cancel channel.

Timers go through an injectable `after` (default `time.AfterFunc`) and the
expiry loop `Manager.Run` through a ticker, so tests drive the party with a
fake clock instead of sleeping.

## 8. Lazy solving of library puzzles (`web.Library.start`, `internal/web/library.go`)

The library holds about 200 puzzles; solving all at start would take minutes
on a Raspberry Pi. Each entry is solved in the background on the first visit
of its page.

<!-- concviz 08-library-future: generated by go test ./internal/concviz -update -->

![Sequence diagram: 8. Lazy solving of library puzzles: a future from sync.Once and close](concurrency/08-library-future.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#08-library-future) in a browser.

1. Visitor 1 opens a library puzzle (page #1). Building the page, done() peeks at e.ready with a select with default: it never blocks.
2. Then lib.start calls once.Do. The first call starts the solver goroutine, whose defer close(e.ready) is the promise.
3. Later the page asks /bibliothek/weg for the trace (/weg #1). once.Do does nothing now; the handler waits on e.ready or its request.
4. A second visitor asks too (/weg #2). Any number of goroutines can wait on the same channel.
5. Visitor 1 closes the tab, which cancels their request: that handler returns. The solver goes on for whoever comes next.
6. The solver sets sol, res and err, then its deferred close(e.ready) wakes every waiter at once.
7. What was written before the close is safe to read after the receive: no lock needed for e.res.
8. A closed channel stays ready forever: for visitor 3 (page #3), done() is true at once and the page carries the trace.

<!-- /concviz -->

- **A future built from `sync.Once` and a channel.** `start` runs the solver
  in a goroutine exactly once (`once.Do`) and `defer close(e.ready)`.
  Closing is the signal: every present and future receiver sees it, any
  number of times. The fields written before the close are safe to read
  after receiving from `ready`.
- **Peeking**: `done()` is a non-blocking `select` with `default`.
- **Waiting with a way out**: the handlers that need the result `select` on
  `e.ready` and `r.Context().Done()`. If the visitor leaves, the handler
  returns, but the solve goes on and its result waits for the next visitor.

## 9. Live party updates (`party.Manager.Subscribe`, `web` `/party/{code}/events`)

Every player's browser holds a server-sent events stream; every change of a
party must reach all of them.

<!-- concviz 09-party-events: generated by go test ./internal/concviz -update -->

![Sequence diagram: 9. Live party updates: coalescing signals feeding server-sent events](concurrency/09-party-events.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#09-party-events) in a browser.

1. Two players have the party open; each browser holds an event stream. Subscribe makes a channel with a buffer of 1 per stream, and the handler sends the current state.
2. Both wait in a select on three channels: their request's context, the change signal, and a heartbeat ticker.
3. A player gets ready. The request, holding pm.mu, broadcasts: signal does a non-blocking send to each stream. Both wake up and send version 2.
4. Stream A is quickly back in its select. Stream B's client is slow: B is still writing.
5. Two changes in a burst (versions 3 and 4). A takes the first signal at once, the second waits in its slot. B's slot holds one already, so the second is dropped. The publisher never blocks.
6. Nothing is lost: a signal carries no data, and the stream reads the current state when it wakes. B finds its pending signal and sends version 4, which has both changes. So does A.
7. Twenty quiet seconds later the ticker fires. A writes a comment line, a keep-alive that stops proxies from closing an idle connection.
8. Player B closes the tab: their request's context is cancelled. B's select returns, and the deferred cancel unsubscribes its channel.
9. Player A leaves too, the stream stays open. When the party expires, Tick signals its streams once more; A's Snapshot fails, so it sends a final gone event and returns.

<!-- /concviz -->

- **Coalescing notifications.** `Subscribe` creates a `chan struct{}` with
  capacity 1 per stream; `signal` does a non-blocking send. Many changes in a
  burst collapse into one pending signal. Nothing is lost because the signal
  carries no data: the stream reads the *current* state (`Snapshot`) when it
  wakes. "Signal that something changed, then read the state" avoids slow
  subscribers blocking the publisher, and needs no buffer sizing.
- **Signalling under the lock.** `broadcast` runs while the manager's mutex
  is held; that is fine only because `signal` never blocks.
- **Unsubscribe** is the returned `cancel` func, deferred by the handler.
- **The stream loop** `select`s on three channels: the request context (the
  browser left, or the server shuts down), the change signal, and a 20 s
  `time.Ticker` for a keep-alive comment that stops proxies from closing an
  idle connection. A party that expires signals its subscribers once more;
  their `Snapshot` fails and they send a final `gone` event.

## 10. Process lifecycle (`cmd/starbattle/main.go`)

`serve`, `design` and `hardsearch` end cleanly on Ctrl-C or a systemd stop;
the run below follows `serve`.

<!-- concviz 10-process-lifecycle: generated by go test ./internal/concviz -update -->

![Sequence diagram: 10. Process lifecycle: signal context, ticker loop, graceful shutdown](concurrency/10-process-lifecycle.svg)

To step through the scene, open [`concurrency/player.html`](concurrency/player.html#10-process-lifecycle) in a browser.

1. serve: signal.NotifyContext turns Ctrl-C and SIGTERM into a cancelled ctx. The party manager's loop runs as Run(5 s, ctx.Done()): a select on a ticker and a stop channel.
2. ListenAndServe blocks for the server's whole life, so it runs in a goroutine of its own and will send its error on errc, a channel with capacity 1.
3. The main goroutine waits for whichever comes first: an error of the server, or the end of ctx.
4. Every 5 seconds the ticker fires: Run wakes up and calls Tick (sections 7 and 9).
5. Then it selects again, until the next tick or the stop.
6. Ctrl-C: ctx is cancelled, its Done channel closed. Both selects wake up: Run returns, serve goes on to shut down. Request contexts derive from ctx (BaseContext), so open event streams end as well.
7. serve calls srv.Shutdown. ListenAndServe returns ErrServerClosed and sends it on errc. Nobody reads errc any more, but its one slot takes the value, so the goroutine finishes instead of leaking.
8. Shutdown returns once the open requests are done. serve returns and the process exits.

<!-- /concviz -->

- `signal.NotifyContext` turns Ctrl-C and SIGTERM (systemd stop) into a
  cancelled context, used by `serve`, `design` and `hardsearch`.
- `http.Server.BaseContext` makes every request context a child of it, so
  long-lived requests (event streams, design completions) end on shutdown and
  `Shutdown` does not wait for them until its timeout.
- `ListenAndServe` runs in a goroutine that sends its error on `errc`, a
  channel with **capacity 1**: after a shutdown nobody reads it any more, and
  the buffer lets the goroutine finish instead of leaking. The main goroutine
  `select`s between that error and the context.
- `Manager.Run(interval, ctx.Done())` shows the plain "ticker + stop channel"
  loop.

## Idioms

| Idiom | Used in |
|---|---|
| `close(ch)` as a broadcast to any number of receivers | `quit` (1), `jobs` (2, 4), `out`/`results` (4, 5), `ready` (8) |
| capacity-1 channel + non-blocking send = coalescing wake-up | `mailbox.notify` (1), `signal` (9) |
| mutex-protected slice + notify channel = unbounded queue | `mailbox` (1) |
| buffered channel as counting semaphore | `slots`, `cpuSlots` (3) |
| buffered channel sized so sends can never block | `out` in (5), `queue` (6), `errc` (10) |
| `select` with `default` to poll | `cancelled` (3), `done()` (8), `signal` (9) |
| `<-chan struct{}` for cancellation in lower packages, `context` at the edges | generator, hardsearch, designer |
| waiter goroutine `wg.Wait(); close(out)` so the consumer can `range` | (4), (5) |
| results written by index instead of sent | `hyps` (2), `results` (3) |
| `sync.WaitGroup.Go` (Go 1.25) instead of `Add`/`Done` | (1), (2), (3), (4), (5) |
| no channel at all: mutex + generation number | (7) |
